# Consistency review: specification ↔ Phase I ↔ Phase II ↔ implementation

This file records every gap or contradiction found while rebuilding BookOrbit AI
from the project specification, the graded Phase I report and the Phase II design
report, and how the implementation resolves it. Items marked **Report fix** are
changes the Phase II report should get so that report and code say the same thing.

## A. Professor's feedback on Phase I (grade 90)

| # | Feedback | Resolution |
|---|----------|------------|
| A1 | "In the use case diagram there are 18 cases, but in your descriptions only 8 are given." | Phase II already describes all 18. The implementation now has **one service method, one screen and automated tests for each of the 18 use cases** - see [TRACEABILITY.md](TRACEABILITY.md). Nothing in the diagram is left without code. |
| A2 | Flowcharts 3.2-1 … 3.2-4 "are not needed in the spec, can be reused in the design report." | The flows they show are the flows implemented (login, purchase, chatbot routing, review moderation). **Report fix:** they can be added to Phase II Section 2 next to UC-02, UC-08, UC-12 and UC-10, updated with items B6 and B7 below. |

## B. Contradictions and gaps, and what the code does

| # | Where | Problem | What the implementation does |
|---|-------|---------|------------------------------|
| B1 | Phase I §3 vs Phase I §1.3 / Phase II UC-11 | Phase I §3 says a VC is demoted after **more than two warnings**; the glossary and Phase II say a VC is demoted after **one blocked comment**. (Phase II memo 11/10 says this was fixed.) | Phase II rule, which is also the spec's wording: a blocked comment gives the VC a warning and demotes them to RC at once; promotion counters restart. `WarningService.issue`. |
| B2 | Fig. 22 (Registration) vs UC-01 and spec item 4 | The screen has **password** fields and "Face sign-in (optional)". UC-01 has **username + face photo, no password**, and the spec requires RC/VC/SU to log in with a face and/or voice sample. | Followed UC-01 and the spec: Full name, **Username** (added - UC-01 needs it), Email, **required** face capture, terms checkbox, "Continue as a visitor". No passwords anywhere. Same split layout as Fig. 22. **Report fix:** redraw Fig. 22. |
| B3 | Fig. 25 (Checkout) vs UC-08 | The screen shows a **multi-book cart** and a **"Discount code"** box; UC-08 describes a single "Buy Now", and no discount codes exist in the spec. | Cart kept (it is in both mock-ups): each book becomes its own UC-08 purchase record and ledger line; the balance check and the $1 fine apply once per order. The discount-code box is replaced by the automatic **VIP −10%** line. "Buy now" on a book goes straight to checkout with that book first. **Report fix:** mention the cart in UC-08 and remove "discount code" from Fig. 25's caption. |
| B4 | Fig. 20 (E-R diagram) vs Section 4.1 / the class diagram | The E-R diagram models things the design does not have (Shipping Address, Payment, Inventory, Publisher, Order Discount, Customer Order / Order Item, password hash, Visitor Session, Penalty…) and misses things it does have (transaction ledger, login attempts, reading progress, status changes, admin actions, RAG chunks, face templates). Many entities have no attributes or key, but the assignment requires "attributes and key for each class". | New diagram generated from the code: [`docs/ER_diagram.png`](ER_diagram.png) (`python tools/make_er_diagram.py`). 15 entities = the 15 `data/*.txt` files, **every attribute listed, keys underlined, foreign keys marked**, with cardinalities. **Report fix:** replace Fig. 20. |
| B5 | UC-10 actors (RC, VC) vs spec item 7 and Phase I UC-04 | Spec: "**Any user** can comment on any book with 1-5 stars". Phase I listed VS and SU as actors; Phase II dropped them. | Any user can review. Visitor and SU reviews have weight 1.0; a blocked visitor/SU comment is simply blocked (there is no customer account to warn or suspend). One review per user (or per visitor session) per book; writing again edits it ("Edit review" in Fig. 24). **Report fix:** UC-10 actors → VS, RC, VC, SU. |
| B6 | UC-12 pseudo-code vs spec item 9 | If Ollama is not running, UC-12 shows "offline" for **every** question, so store questions can't be answered either. Spec item 9 says check the local files first and answer from them. | RAG first, always: store/catalog answers come from the local files and are labelled "[Store data] Answered via RAG…". With the LLM on, it phrases the retrieved text; with the LLM off, the matching passage is shown. Only general questions need the LLM ("[General AI] … answered by the local LLM (Ollama, model)"). |
| B7 | UC-12 vs spec item 3 | Spec: answers for VS, RC, VC and SU are "**increasingly more**". Phase II only separates visitors from signed-in users. | Permission matrix (also in `chatbot_service.py`): VS store info only · RC + own account + general LLM questions · VC + search inside the full texts of every book + VIP savings · SU + finance report, suspended accounts, warnings, order lists (UC-13). **Report fix:** add the matrix to UC-12. |
| B8 | UC-02 pseudo-code `threshold = 0.60` | Too strict for the SFace embedding (its published cosine threshold is 0.363); genuine users under different light would be rejected. | Threshold **0.40**, configurable (`BOOKORBIT_FACE_THRESHOLD`). Measured on test photos: same person after rotation/lighting changes 0.93-0.98, a different person 0.23. **Report fix:** 0.60 → 0.40 in UC-02. |
| B9 | Fig. 21 footer "Mock AI (LLM_MODE=mock) / Mock biometrics", `requirements-real.txt` in §7 | The design shows mock modes. | No mocks in the application: real YOLOv8-face detector + SFace embedding, real Ollama HTTP client. The sidebar shows the **live** status of Ollama and the face models. Test doubles exist only in `tests/`. |
| B10 | Design screens vs spec note 4 | The mock-ups use invented books ("A House of Folded Letters", "Salt and Static"…). | 32 public-domain books; 17 have their full Project Gutenberg text (via the NLTK Gutenberg corpus) for the Reading Companion and RAG. Covers are generated in the mock-ups' style (`tools/make_covers.py`). |
| B11 | UC-17 vs spec item 6 | Spec: the customer "must ask the SU to reopen the account **with positive money deposited**". Phase II: the customer deposits first in wallet-only mode. | Both ways work: the customer deposits in wallet-only mode, **or** the SU records the deposit in the Reopen form. Rule: balance must be **$0 or more**; otherwise "The customer must deposit at least $X first". Reopening resets warnings to 0. |
| B12 | Spec item 6 "suspended (cannot log in)" vs Phase II "wallet-only mode" | A suspended customer who cannot sign in cannot deposit. | Kept Phase II's wallet-only mode: after face sign-in, **only My Balance** can be opened until an SU reopens the account (every other page redirects there). |
| B13 | UC-02 "Face template missing - contact a Super-User" | No use case or screen lets an SU give a user a face template. | User Management has **Enrol face / Replace** for every account (camera or photo), and `tools/enroll_face.py` does the same from the command line (used to set up the demo accounts). Logged as `ENROLL_FACE`. |
| B14 | Collaboration diagram files vs Section 4.1 | Store information for RAG (`policies.txt`) is used but not shown; face templates are `.npy` files plus an index. | `data/policies.txt` = store/team information (spec item 9); `data/biometrics.txt` indexes `data/biometrics/<user_ID>_face.npy`. **Report fix:** add `policies.txt` to Fig. 1. |
| B15 | UC-04 "If the cover-search model is not loaded…" | Cover search needs no downloaded model in the implementation. | SIFT key-points + RANSAC homography + colour histogram (OpenCV only). The button is disabled only if no cover is indexed yet. Text search always works. |
| B16 | UC-14 alternative flow "If the LLM is offline, the AI buttons show an offline message" | All companion tools would stop working without Ollama. | Summarize (extractive), Quiz me (fill-in-the-blank) and Ask (best passage via RAG) still work offline; only Explain and Define need the LLM. Quiz answers stay on the server until the reader answers. |
| B17 | Section 5 (System Screens) | Only 5 of the screens are designed. | The other screens use the same layout and components: Sign in, My Balance, Receipt, My Orders, My Reviews (with warnings), Recommendations, AI Chatbot, Reading Companion, Manage Books, Taboo Words, User Management, Reports. **Report fix:** add screenshots (`tests/e2e_browser.py` saves them). |
| B18 | Section 7 repository tree | Lists files of the earlier prototype (`rules.py`, `requirements-real.txt`, `CLAUDE.md`, …). | **Report fix:** replace with the tree in the README. |
